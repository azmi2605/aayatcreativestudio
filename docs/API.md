There is no custom REST API server. Most "endpoints" are generated by Supabase from the database and protected by DATABASE.md's row-level security. Only two endpoints are written by us (`submit-enquiry` and `retry-notifications`).

## 1. API Overview

### 1.1 Principles

- **Define only required APIs.** Every endpoint traces to a PRD journey. Anything else is not exposed.
- **Authorization is enforced on the server.** Row-level security, Storage policies and function checks decide access. Client-side admin guards only improve the experience and are never relied on.
- **No secrets in the browser.** The browser holds only the public project URL and the publishable key. Everything else is server-side.
- **Default deny, then allow.** Anonymous callers can only read published content and submit an enquiry.
- **One convention per concern.** One error format, one pagination style, one naming rule per surface (section 2).
- **Every integration is fault-tolerant.** A failing third party never loses a lead, blocks a visitor or breaks a page (section 16).

### 1.2 API surfaces

| Surface | Provided by | Used by | Defined in |
|---|---|---|---|
| Data API (REST over the database) | Supabase PostgREST | Visitors (read), admin (read and write) | Sections 5 and 7 |
| RPC endpoints (database functions) | Supabase PostgREST | Admin | Section 7.3 |
| Auth API | Supabase Auth | Admin | Section 7.2 |
| Storage API | Supabase Storage | Admin (upload, delete), everyone (read images) | Sections 5.6 and 7.5 |
| `submit-enquiry` | Our Edge Function | Visitors | Section 6 |
| `retry-notifications` | Our Edge Function | Scheduler only | Section 8 |
| Email API | Resend | Our Edge Functions | Section 11 |

### 1.3 Base URLs

`{SUPABASE_URL}` is the project URL for the environment (public, from the site configuration). `{SITE_URL}` is the site's own origin.

| Surface | Base path |
|---|---|
| Data API and RPC | `{SUPABASE_URL}/rest/v1/` |

| Storage | `{SUPABASE_URL}/storage/v1/` |

Static pages are served from `{SITE_URL}` and are not part of this API.

## 2. Conventions

### 2.1 Protocol

| Topic | Rule |
|---|---|
| **Transport** | HTTPS only. Plain HTTP is never used. |
| **Format** | JSON, UTF-8, for every request and response body defined here. File uploads are binary (section 7.5). |
| **Methods** | GET read, POST create or action, PATCH partial update, DELETE remove. No PUT for application data. |
| **Timestamps** | ISO 8601 in UTC (for example `2026-10-19T08:30:00Z`). |
| **Identifiers** | UUID strings. Slugs follow DATABASE.md section 6.1. |
| **Booleans, numbers** | Real JSON booleans and numbers, never strings. |
| **Empty values** | Optional fields are omitted or `null`, never empty strings. Empty strings are converted to `null` by the client before sending. |

### 2.2 Field naming [DECISION NEEDED AP-3]

| Surface | Naming | Reason |
|---|---|---|
| Data API and RPC | `snake_case` | Mirrors database column names. Not reshaped. |
| Edge Functions (`submit-enquiry`) | `camelCase` | Matches the shared enquiry contract (ARCHITECTURE 8.2, DATABASE 6.5) |
| Enum values on the wire | `snake_case` codes (for example `ad_creatives`) | Match the database enums. Labels shown to people are the client's content (DESIGN microcopy). |

**Rule:** the data-access modules in the front end are the only place that translates between conventions. UI code never sees raw wire names from two conventions mixed.

### 2.3 Standard request headers

| Header | When | Value |
|---|---|---|
| `apikey` | Every Data API, Auth, Storage and RPC call | The publishable key (public by design) |
| `Authorization: Bearer <access token>` | Admin calls only | The admin's session token from Supabase Auth |
| `Content-Type: application/json` | Requests with a body | Required by `submit-enquiry`, which rejects anything else |
| `Accept: application/json` | JSON reads | Standard |
| `Accept: application/vnd.pgrst.object+json` | Reads that must return exactly one object (for example by slug) | Returns an error if there are zero or many rows |
| `Prefer: return=representation` | Admin writes that need the saved row back | Standard. Otherwise `return=minimal`. |
| `Prefer: count=exact` | Paginated admin enquiry list | Returns the total in `Content-Range` |

The secret key is never sent from a browser, never placed in a header by client code and never appears in any response.

### 2.4 Standard response headers (Edge Functions)

| Header | Value |
|---|---|
| `Content-Type` | `application/json; charset=utf-8` |
| `Cache-Control` | `no-store` |
| `X-Content-Type-Options` | `nosniff` |
| `X-Request-Id` | A fresh UUID per request, also placed in every error body and in logs (section 16.6) |
| `Access-Control-*` | See 2.6 |

### 2.5 Caching

| Request | Rule |
|---|---|
| Public Data API reads | Fetched once per page load. No client-side caching between pages in MVP (stale content after an admin edit is worse than one extra small request). [ASSUMPTION] |
| Admin requests | Always sent with caching disabled (`no-store`), because responses contain personal data and must be fresh |
| Image files (PUB-6) | Immutable. File names are unique and never overwritten, so they are cached for a year (set at upload, section 7.5) |
| Edge Function responses | `no-store` |

### 2.6 CORS

| Surface | Rule |
|---|---|
| Edge Functions | Allow only the configured origins (`ALLOWED_ORIGINS`: production domain, plus the dev preview domain pattern in the dev project only, plus `localhost` locally). Echo back the matching origin, never a wildcard. Methods: `POST` and `OPTIONS` only. Headers: `Content-Type`, `apikey`. Preflight cache: 24 hours. `retry-notifications` sends no CORS headers at all. |
| Data API, Auth, Storage | CORS is handled by Supabase and is open to browsers. Security does not depend on CORS here. It depends on row-level security, Storage policies and tokens. |

CORS and origin checks stop casual cross-site abuse by browsers. They do not stop non-browser clients, which can fake headers. Real protection is validation, rate limiting and the honeypot (sections 6 and 13).

### 2.7 Versioning and change policy

- No URL versioning in MVP. The site, functions and schema deploy together (ARCHITECTURE 8.4).
- Changes are **additive first** (expand, then contract): the server accepts both old and new shapes, then the client is updated, then the old shape is removed. This protects a visitor whose page was loaded just before a deploy.

## 3. Authentication and Authorization

### 3.1 Credentials

| Credential | Held by | Purpose |
|---|---|---|
| Publishable key | Browser (public by design) | Identifies the project for anonymous calls. Grants nothing beyond what row-level security allows to the anonymous role. |
| Access token (short-lived) and refresh token | Admin browser, issued by Supabase Auth after sign-in | Proves the admin is signed in. Sent as a bearer token. Refreshed automatically by the client. |
| Secret key | Edge Functions and CI only | Privileged database access, bypasses row-level security. Never in the browser, the repository or any response. |
| Cron shared secret | Scheduler and `retry-notifications` only | Proves a call to the retry function comes from the scheduler |
| Resend API key | Edge Functions only | Sends email |

### 3.2 Authorization model (server-side)

| Role | Identity | Can do |
|---|---|---|
| Visitor | Publishable key only | Read published content (PUB-1 to PUB-4, PUB-6). Submit an enquiry (PUB-5). |
| Admin | A signed-in user for whom `is_admin()` is true | Everything in sections 7.2 to 7.5 |
| System | Scheduler with the cron secret, or Edge Function with the secret key | SYS-1 and the privileged writes inside functions |

**Rules:**

- Being signed in is not enough. Every admin policy calls `is_admin()` (DATABASE 10). A signed-in user who is not listed as admin has no rights.
- Every authorization decision is made on the server (database policies, Storage policies, function checks). The admin pages hide their content until ADM-1 confirms the admin, but that is only a courtesy.
- Revoking the admin row takes effect on the next request, without waiting for the token to expire.
- Public sign-up is disabled in Auth. The sign-up endpoint is never called and must return an error.
- Functions never trust values from the client for identity or permissions.

### 3.3 Access matrix

| ID | Endpoint | Visitor | Admin | System |
|---|---|---|---|---|
| PUB-1 to PUB-4 | Read published content | Yes (published rows only) | Yes | n/a |
| PUB-5 | Submit enquiry | Yes | Yes | n/a |
| PUB-6 | Read image files | Yes | Yes | n/a |
| AUTH-1 to AUTH-5 | Sign in, refresh, sign out, reset | Credential checks apply | Yes | n/a |
| ADM-1 | Am I admin? | Returns false or is denied | Yes | n/a |
| ADM-2 to ADM-22 | Admin data and files | No | Yes | n/a |
| SYS-1 | Retry notifications | No | No | Yes (cron secret) |

## 6. Enquiry Endpoint: submit-enquiry (PUB-5)

### 6.1 Summary

| | |
|---|---|
| **Method and path** | `POST {SUPABASE_URL}/functions/v1/submit-enquiry` |
| **Purpose** | Validate a project enquiry, protect against abuse, store it and trigger the owner notification (PRD FR-13 to FR-17, ARCHITECTURE DF-2) |
| **Authentication** | None required. The function does not require a signed-in user, so the platform's token requirement is switched off for this function only (verify at setup). It protects itself with the checks in 6.3. |
| **Content type** | `application/json` only |
| **Idempotent** | Yes, by `submissionId` |

### 6.2 Request body

Rules are defined in the shared enquiry contract. Field meanings match DATABASE 6.5.

| Field | Type | Required | Rules |
|---|---|---|---|
| `submissionId` | string | Yes | UUID, generated by the browser when the form first renders |
| `name` | string | Yes | 1 to 100 characters after trimming, single line |
| `brandName` | string | Yes | 1 to 100 characters, single line |
| `email` | string | Yes | Valid email format, up to 254 characters, no whitespace or line breaks. Stored lowercase. |
| `phone` | string or null | No | Digits with common separators (`+` `(` `)` `-` `.` space), 5 to 30 characters |
| `service` | string | Yes | One of `ad_creatives`, `poster_design`, `social_media_design`, `other` |
| `projectDetails` | string | Yes | 20 to 1000 characters after trimming, line breaks allowed |
| `budgetRange` | string or null | No | One of the configured option codes (AD-10). Until defined, the single code `not_sure_yet`. Up to 60 characters. |
| `referenceLink` | string or null | No | Starts with `http://` or `https://`, no whitespace, up to 500 characters |
| `timeline` | string or null | No | Up to 100 characters, single line |
| `website` | string | Honeypot | Must be empty or absent. Hidden from people and assistive technology (DESIGN 11.2). |

No other fields are accepted. Unexpected fields cause a validation error (`unknown_field`), so a mismatch between the client and the contract is caught early [DECISION NEEDED AP-2].

**Example request:**

```json
{
  "submissionId": "3f2b8c1e-9d4a-4b6e-8a53-1c7e2f9a0b44",
  "name": "Riya Shah",
  "brandName": "Sunday Soaps",
  "email": "riya@example.com",
  "phone": "+91 98765 43210",
  "service": "poster_design",
  "projectDetails": "We need three festive poster designs for our new soap range, launching next month.",
  "budgetRange": "not_sure_yet",
  "referenceLink": "https://example.com/our-brand-guide",
  "timeline": "Two weeks",
  "website": ""
}
```

### 6.3 Processing order

Checks run in this order and stop at the first failure. Cheap checks come first.

| Step | Check | Failure response |
|---|---|---|
| 1 | Method is `POST` (or `OPTIONS` for preflight) | 405 with an `Allow` header |
| 2 | Origin is in the allow-list | 403 `origin_not_allowed` |
| 3 | `Content-Type` is `application/json` | 415 `unsupported_media_type` |
| 4 | Body size is at most `MAX_BODY_BYTES` (read with a hard cap, not trusting `Content-Length`) | 413 `payload_too_large` |
| 5 | Body parses as a JSON object | 400 `invalid_json` |
| 6 | Honeypot: `website` is non-empty | 200 success response (identical to a real one). Nothing is stored. A counter metric increments (no personal data logged). |
| 7 | Normalize: remove disallowed control characters, trim, lowercase the email. Then validate every field and collect all errors. | 400 `validation_failed` with a field map |
| 8 | Rate limit (section 13) | 429 `rate_limited` with `Retry-After` |
| 9 | Insert the enquiry under its `submissionId` (a repeat is ignored) | 500 or 503 on database failure |
| 10 | Respond success. After responding, attempt the owner email in the background (EXT-1). | |

**Notes:**

- Rate limiting counts only requests that passed validation (the ones that would write). A visitor correcting form errors does not use up their allowance. Invalid-request floods cost only function invocations, bounded by the plan's quotas (accepted risk).
- A failure to check the rate limit (database unavailable) fails closed: respond 503 and store nothing, because the insert would fail too.
- Spam bots that fill the honeypot receive success and learn nothing.

### 6.4 Success response

HTTP 200, returned for a new enquiry, for a repeated `submissionId` and for a honeypot hit alike:

```json
{
  "ok": true,
  "submissionId": "3f2b8c1e-9d4a-4b6e-8a53-1c7e2f9a0b44"
}
```

The response never contains submitted personal data. The email attempt happens after the response, so its outcome is never part of it.

### 6.5 Error responses

All errors use the standard envelope (section 9.2). Example validation error:

```json
{
  "error": {
    "code": "validation_failed",
    "message": "One or more fields are invalid.",
    "fields": {
      "email": { "code": "invalid_format" },
      "projectDetails": { "code": "too_short", "min": 20 }
    }
  },
  "requestId": "7b0c9a52-1d1f-4f0b-9f0e-5d9a4b6c1e21"
}
```

| Status | `error.code` | Meaning | Client behavior (DESIGN 11.2) |
|---|---|---|---|
| 400 | `validation_failed` | One or more fields invalid. `fields` maps field name to a code. | Inline field errors, form-level banner, focus first invalid field, keep input |
| 400 | `invalid_json` | Body is not valid JSON | Generic retry banner (should not happen from the real form) |
| 400 | `validation_failed` with field code `unknown_field` | Unexpected field | Generic retry banner (contract mismatch) |
| 403 | `origin_not_allowed` | Request came from a non-allowed origin | Generic retry banner |
| 405 | `method_not_allowed` | Wrong method | n/a |
| 413 | `payload_too_large` | Body exceeds the cap | Generic retry banner |
| 415 | `unsupported_media_type` | Not JSON | n/a |
| 429 | `rate_limited` | Too many attempts. `Retry-After` header and `retryAfterSeconds` in the body. | Banner: "Too many attempts, please try again later", plus fallback contacts |
| 500 | `server_error` | Unexpected failure | Banner with Retry and Instagram/email fallback, input kept |
| 503 | `unavailable` | Database or dependency unavailable, or rate-limit check failed | Same as 500 |

### 6.6 Idempotency and retries

- A repeated `submissionId` returns the same success response and stores one enquiry (primary key, DATABASE 6.5).
- After a failure or lost response, the visitor presses Retry and the browser re-sends the same `submissionId`. There is no silent automatic retry of this POST (section 16.2).
- Each retry still counts toward the rate limit once it passes validation.

### 6.7 What the endpoint writes and triggers

| Effect | Detail |
|---|---|
| Database | One row in `enquiries` (`status` new, `notified_at` empty), written with the secret key inside the function |
| Rate-limit counters | Two increments in `private.rate_limits` through `check_rate_limit` (per caller per hour, global per day) |
| Email | Background attempt via EXT-1. On success sets `notified_at`. On failure leaves it empty for SYS-1. |
| Logs | Request ID, outcome code, enquiry ID, duration. No personal data. |

## 7. Admin Endpoints

All admin endpoints require the admin's access token and are enforced by row-level security and Storage policies. Admin pages call ADM-1 first, on every page load, before showing any admin content.

### 7.1 Admin session flow

1. AUTH-1 signs in with email and password.
2. The client calls ADM-1. If the result is not `true`, it signs out (AUTH-3) and shows the generic invalid-credentials message (DESIGN 12.2).
3. The session is renewed with AUTH-2 before expiry (done by the client library).
4. AUTH-3 signs out. The client clears the stored session.

### 7.2 Auth endpoints (Supabase Auth)

| ID | Purpose | Request | Notes |
|---|---|---|---|
| AUTH-1 | Sign in | Email and password | Failure returns a generic invalid-credentials error. The UI must not say which part was wrong (DESIGN 12.2). |
| AUTH-2 | Refresh | Refresh token | Done by the client library |
| AUTH-3 | Sign out | Access token | Ends the session |
| AUTH-4 | Request reset email | Email, and a `redirect_to` URL that must be on the Auth allow-list (the `/admin/reset` page for each environment) | Always shows the same neutral message ("If that email exists, a reset link was sent"), whether or not the account exists |
| AUTH-5 | Set new password | New password, sent from the recovery session created by the reset link | Password rules: minimum length [ASSUMPTION] 12 characters. Leaked-password checking if the plan supports it (verify at setup). |

Auth rate limits are configured in the platform (section 13.3). Auth emails are sent through Resend's SMTP (EXT-2).

| ADM-17 | List | GET with pagination, optional `status` filter, newest first (section 10.2). Select only `id`, `name`, `brand_name`, `service`, `status`, `notified_at`, `created_at`. | List excludes email, phone and free text (data minimization) |
| ADM-18 | Get one | GET by `id`, single object, all columns | Shows full detail (FR-21) |

There is no create endpoint for enquiries for the browser. Only PUB-5 creates enquiries.

### 7.5 File endpoints (Storage)

| ID | Purpose | Request |
|---|---|---|
| ADM-21 | Upload a file | `POST /storage/v1/object/site-images/{path}` with the file bytes. Content type `image/webp` or `image/jpeg`. Overwrite is not allowed. Cache header set to one year (names are unique). |
| ADM-22 | Delete files | `DELETE /storage/v1/object/site-images` with a list of exact paths, or DELETE on one path |

**Rules:**

- Paths follow DATABASE section 12. Each uploaded file gets a new, unique name. Replacing an image means uploading a new file, then deleting the old one.
- Limits: 3 MB per file, allowed types WebP and JPEG (DB-3). Violations return an error from Storage (section 9.4).
- The browser prepares the files first (re-encode, resize, strip metadata). Server-side limits are the real enforcement.
- **Order for a new image:** upload all variants, then ADM-7. **Order for removal:** delete files, then the row. A failure between the two steps leaves harmless orphan files, never broken rows (DATABASE 12).

## 8. System Endpoint: retry-notifications (SYS-1)

### 8.1 Summary

| | |
|---|---|
| **Method and path** | `POST {SUPABASE_URL}/functions/v1/retry-notifications` |
| **Purpose** | Guarantee the owner is notified of every enquiry, even if the first email attempt failed (ARCHITECTURE 3.2, DATABASE Q7, Q8, Q16) |
| **Caller** | The database scheduler only, every 10 minutes |
| **Authentication** | `X-Cron-Secret` header with the shared secret. No user token. |
| **CORS** | None. It is never called from a browser. |

### 8.2 Behavior

1. Reject any request without the correct secret: 401 with an empty error body. The comparison is constant-time. Wrong method: 405.
2. Select up to `NOTIFY_BATCH_SIZE` enquiries where `notified_at` is empty, created within the last `NOTIFY_RETRY_WINDOW_DAYS` days, oldest first.
3. For each, build and send the email (EXT-1) with the enquiry ID as the idempotency key. On success set `notified_at`.
4. Sends are sequential with a short pause, to stay under the email provider's rate limit.
5. If a send fails with an authentication or configuration error (the provider rejects the API key or sender), stop the batch immediately (retrying 20 doomed calls helps nobody) and log the failure.
6. If a send fails with a transient error (timeout, rate limit, server error), skip it and continue. It is retried in the next run.
7. Return a summary.

### 8.3 Response

| Status | Body |
|---|---|
| 200 | `{ "ok": true, "processed": n, "sent": n, "failed": n }` |
| 401 | Empty body (no hint about why) |
| 405 | Standard error envelope |
| 500 | Standard error envelope |

### 8.4 Daily cleanup

The cleanup of expired rate-limit rows (DATABASE Q15) is a direct scheduled database job, not an HTTP endpoint.

## 9. Validation and Error Conventions

### 9.1 Validation layers

| Layer | Role | Trusted? |
|---|---|---|
| Browser (forms) | Fast feedback, using the same shared contract rules | No |
| Edge Function | Normalizes and validates against the shared contract. The authority for enquiries. | Yes |
| Database constraints, triggers and row-level security | Final enforcement for everything, including the admin's direct writes (DATABASE 8) | Yes |

One shared contract (rules plus test vectors) is used by the browser, the function and the tests, so client and server cannot drift.

**Who owns wording:** servers return codes. The client owns all user-facing wording (DESIGN microcopy and the "plain language, what to do next" rule). Server messages are for developers and logs only.

### 9.2 Error envelope (all errors we define)

| Field | Type | Meaning |
|---|---|---|
| `error.code` | string | Stable machine code from 9.3 |
| `error.message` | string | Short English description for developers. Never shown to users as-is. |
| `error.fields` | object (optional) | For validation errors: field name to `{ code, min?, max? }` |
| `error.retryAfterSeconds` | number (optional) | For rate limits |
| `requestId` | string | UUID, also in the `X-Request-Id` header |

The envelope never echoes submitted values, never contains stack traces, SQL, internal paths, keys or table names.

### 9.3 Error codes

| Code | HTTP | Used when |
|---|---|---|
| `validation_failed` | 400 | Field validation failed |
| `invalid_json` | 400 | Body is not valid JSON |
| `origin_not_allowed` | 403 | Origin not on the allow-list |
| `method_not_allowed` | 405 | Wrong HTTP method |
| `payload_too_large` | 413 | Body exceeds the cap |
| `unsupported_media_type` | 415 | Wrong content type |
| `rate_limited` | 429 | Too many attempts |
| `server_error` | 500 | Unexpected failure |
| `unavailable` | 503 | Dependency unavailable |

Field-level validation codes: `required`, `too_short`, `too_long`, `invalid_format`, `invalid_option`, `unknown_field`. They carry `min` or `max` where useful.

### 9.4 Errors from Supabase surfaces (mapped by the front end)

The Data API, Auth and Storage return their own error formats. The data-access modules map them to a small set of categories (ARCHITECTURE 12.2) so the UI never parses raw errors.

| Source signal | App category | Typical UI result |
|---|---|---|
| Network failure, timeout, 502, 503, 504 | `network` | Retry state (DESIGN 12.2) |
| 401, or 403 from row-level security | `permission` | Public: treated as unavailable. Admin: go to sign-in. |
| Single-object request found nothing | `not_found` | "This work isn't available" |
| 409 or unique violation | `conflict` | Admin message (for example slug or image order clash) |
| Check or trigger violation | `validation` | Admin field or banner message (9.5) |
| Auth: invalid credentials | `invalid_credentials` | Generic message (DESIGN 12.2) |
| Auth: rate limited (429) | `rate_limited` | "Too many attempts, please try again later" |
| Storage: wrong type, too large (413), exists | `upload_rejected` | Specific upload message (DESIGN 11.3) |
| Anything else | `unknown` | Generic error with retry |

### 9.5 Database rule errors the admin must handle

Constraint names follow `<table>_<column>_<rule>` (DATABASE section 4). The following stable identifiers are raised by the database triggers (amendment A1 in section 18). Each maps to one fixed message in the admin UI.

| Identifier | Meaning | Admin message (client wording) |
|---|---|---|
| `publish_requires_alt_text` | Publishing without alt text | "Add alt text before publishing" |
| `publish_requires_image` | Publishing without an image | "Add at least one image before publishing" |
| `last_image_required` | Removing the last image of a published item | "A published item needs at least one image" |
| `slug_immutable` | Changing the slug of a published item | "The link for a published item can't change" |
| A check constraint name | A field failed a database check | Mapped to the field named in the constraint |

## 10. Pagination, Filtering and Ordering

### 10.1 Public list: no pagination in MVP

- The published list (PUB-2) is fetched once and filtered in the browser. This is correct up to about 100 items (ARCHITECTURE 6.4).
- The request sets an explicit limit of 200 so unexpected growth is visible rather than silently truncated at the platform's default cap.
- **Category filter:** the category is held in the page URL as a query value (for example `?category=ads`). The client validates it against the three enum values before use. Unknown values show "All".
- "Featured" for Home is a client-side filter on the same list.
- **When this changes:** more than about 100 published items, or slow first loads. Then use server-side filtering and pagination, or a cached snapshot (ARCHITECTURE 17.2).

### 10.2 Admin enquiries: paginated

| Parameter | Rule |
|---|---|
| Page size | 25 by default, maximum 100 [DECISION NEEDED AP-4] |
| Paging style | Offset and limit (adequate at this volume, with the `created_at` index from DATABASE 9.3) |
| Order | Newest first by `created_at`, with `id` as a tie-breaker so pages are stable |
| Filter | Optional `status` equal to one of the three enum values, validated before use |
| Total count | Requested with the list (`count=exact`), read from the `Content-Range` response header, used to show "Page 2 of 6" |
| Beyond the end | An out-of-range page returns an empty list. The client shows the empty state for that filter. |

### 10.3 Other admin lists

Items (about 100) and testimonials (about 50) are fetched in full, ordered by `sort_order` descending. No pagination.

### 10.4 Filtering safety

All filter values are validated against their format (enum, UUID, slug) and URL-encoded before use. Free text is never placed into a filter expression.

## 12. Webhooks and Verification

### 12.1 Inbound webhooks in MVP

None. The project does not accept webhooks from third parties.

### 12.2 Scheduler call (internal, webhook-like): SYS-1

The scheduler calls `retry-notifications` over HTTPS. Verification:

| Rule | Detail |
|---|---|

| **Failure** | 401 with an empty body. No hint whether the header was missing or wrong. |

- Respond 2xx quickly. Process safely. Never trust event content to choose database rows beyond a matched, validated enquiry ID.
- No CORS headers. The signing secret stored as a function secret.
- Add a PRD entry first.

## 13. Rate Limiting

### 13.1 Summary

| Surface | Limit | Mechanism | On limit |
|---|---|---|---|
| `submit-enquiry` per caller | 5 valid submissions per hour [ASSUMPTION] | Atomic counter in the database, keyed by a salted hash of the caller's IP | 429, `Retry-After` |
| `submit-enquiry` global | 100 per day [ASSUMPTION] | Same counter with the key `global` | 429 for everyone until the window rolls. A circuit breaker. |
| Auth (sign-in, reset, email sending) | Stricter than the platform defaults (13.3) | Supabase Auth settings | 429 from Auth, mapped to "Too many attempts" |
| Data API reads | No project-level limit. Platform capacity and plan quotas apply. | None | n/a (accepted risk, see 13.4) |
| `retry-notifications` | One run per 10 minutes, batch of at most 20 | Scheduler plus batch size | n/a |
| Outbound email | Under the provider's per-second limit | Sequential sends with pauses | Retry next run |

### 13.2 Caller identification

- The caller key is a keyed hash (HMAC) of the caller's IP address using `IP_HASH_SALT`, taken from the trusted forwarded-address value supplied by the platform's edge, never from a header the client can set (verify which header at setup).
- The raw IP is never stored or logged. The hash expires within about a day (DATABASE 6.7).
- Many people behind one network (an office, a mobile carrier) share a key. Five per hour is generous for a studio enquiry form and the shared case is accepted.
- The counter increment-and-check is a single atomic database operation, so concurrent requests cannot slip past the limit.

### 13.3 Auth rate limits [ASSUMPTION]

Configure in Supabase Auth (verify ranges at setup): a low number of password sign-in attempts per IP per five minutes (for example 10), a low hourly limit on reset emails, and a low email-sending limit. Sign-ups remain disabled.

### 13.4 Accepted risks and escalation

- Published content reads are cheap and public. Flooding them is a cost risk, handled by plan quotas, the spend cap and usage alerts (ARCHITECTURE 15.4, 15.5).
- **Escalation path for enquiry spam** (ARCHITECTURE 17.2): managed bot check or CAPTCHA in front of `submit-enquiry`, then a stricter limit, then temporarily disabling the form behind a static fallback message.

## 15. Data Privacy

### 15.1 Personal data flow

| Data | Enters through | Stored in | Leaves to | Never goes to |
|---|---|---|---|---|
| Enquiry name, email, phone, brand, details, link, timeline | PUB-5 | `enquiries` (admin-only) | The owner, via EXT-1 | Logs, analytics, responses, error bodies, the browser of other visitors |
| Caller IP | PUB-5 request | Only as a salted hash in `rate_limits`, deleted within about a day | Nowhere | Logs, enquiries, analytics |
| Admin email and password | AUTH-1 | Platform Auth | Auth reset emails (EXT-2) | Application tables, logs |
| Published content | Admin writes | Content tables and Storage | Everyone (public by design) | n/a |

### 15.2 Rules

- **Minimization:** responses and requests carry only what each journey needs. Public reads select explicit columns. The admin enquiry list excludes contact details and free text (ADM-17).
- **Responses never echo personal data.** PUB-5 returns only an ID. Error bodies contain codes, never submitted values.
- **Logs:** only request ID, endpoint, outcome code, enquiry ID and duration. Never names, emails, phones, free text, IPs, keys or tokens.
- **Admin responses are never cached** (section 2.5), and the admin pages do not store enquiry data in browser storage beyond what the session needs.
- **Output safety:** all enquiry text is shown as plain text. `referenceLink` is made clickable only after confirming it starts with `http://` or `https://`, opening with the opener and referrer disabled (DATABASE 11.2).
- **Third parties:** the email provider receives the enquiry fields to deliver the owner's email. The platform provider processes all data. Analytics receives no personal data. The privacy note near the form describes this (PRD NFR, D10).
- **Retention and deletion:** enquiries are kept until the admin deletes them (ADM-20). The notification email, provider logs and backups age out separately (DATABASE 11.2, 14.5). *This document is not legal advice. Review the data-protection obligations that apply to the studio's visitors before launch.*
- **Test data:** tests and development use invented data only. Real enquiries are never copied out of production.

## 16. Failure Handling and Resilience

### 16.1 Principles

- A lead is never lost silently: stored first, notified second, retried until noticed.
- A failing third party never blocks a visitor or breaks a page.
- Every outbound call has a timeout. No unbounded waits.
- Errors are mapped to designed states (DESIGN 12). Users never see raw errors.
- Retries happen only where they are safe (idempotent).

### 16.2 Timeouts and client retries

| Call | Timeout | Automatic retry |
|---|---|---|
| Public reads (PUB-1 to PUB-4) | 10 seconds | One retry after about one second on network error or 5xx. Then show the error state with a Retry button. |
| `submit-enquiry` (PUB-5) | 15 seconds | None. The visitor presses Retry, which re-sends the same `submissionId`. The form data is kept. |
| Admin reads | 15 seconds | One retry on network error, then an error banner with Retry |
| Admin writes and uploads | 30 seconds for uploads, 15 seconds otherwise | None. Error banner, input preserved, user retries |
| Image files | Browser default | None. Placeholder shown. |
| Outbound email (EXT-1) | 10 seconds | None in-process. The scheduler retries. |

### 16.3 Failure matrix

| Failure | Detection | Visitor experience | Server behavior | Recovery |
|---|---|---|---|---|
| Data API unavailable | Network error or 5xx | Section hidden (featured, testimonials) or error state with Retry (work list). Header and footer use built-in defaults. | n/a | Automatic when the platform returns |
| Settings row unreadable | PUB-1 fails or empty | Built-in default tagline and contact links | n/a | Admin fixes settings |
| `submit-enquiry` fails or times out | Network error, 500, 503 | Banner with Retry plus Instagram and email fallback. Entered data kept. | A first attempt may have stored the row. A retry with the same ID is safe. | Visitor retries, or uses fallback contacts |
| Rate limit exceeded | 429 | "Too many attempts, try again later" plus fallback contacts | Nothing stored | Wait for the window |
| Database down during a submission | Rate-limit check or insert fails | Same as 500 or 503 | Fails closed. Nothing is stored. | Visitor retries later |
| Email provider down | Failed send | None (invisible to the visitor) | `notified_at` stays empty. Retry every 10 minutes for up to 7 days. | Automatic. Admin shows "Email not sent" meanwhile. |
| Email provider rejects configuration | 401, 403 | None | Batch stops. Error logged every run. | Owner fixes the key or sender. Retries resume. |
| Scheduler stops | Unnotified enquiries accumulate | None | The "Email not sent" indicator and a usage check reveal it | Re-enable the scheduled job. Next run catches up (within the 7-day window). |
| Image upload fails (admin) | Storage error | n/a | n/a | Specific message, input kept, retry |
| Image delete fails (admin) | Storage error | n/a | Rows are not removed until files are gone (or the failure is reported) | Retry. Orphan files are harmless. |
| Admin session expired | 401 | n/a | n/a | Redirect to sign-in. Unsaved form input is preserved where possible. |
| Admin password reset email missing | User reports | n/a | n/a | Recreate access from the platform dashboard (README) |
| Analytics blocked or down | Script fails to load | None | n/a | Ignored silently |
| Whole backend unavailable | All requests fail | Static pages still load. Work list shows error state. Contact page shows fallback contacts. | n/a | Platform recovery |

### 16.4 Idempotency summary

| Operation | Idempotent by |
|---|---|
| PUB-5 | `submissionId` primary key |
| EXT-1 send | Enquiry ID as idempotency key (and `notified_at` check) |
| SYS-1 | Only unnotified rows are processed |
| Admin PATCH and DELETE | Naturally repeatable. A second delete of the same row returns no rows and is treated as success. |
| Admin create (ADM-4, ADM-7, ADM-12) | Not idempotent. The UI disables the button while saving, and shows the saved item before allowing another create. |

### 16.5 Concurrency

Single admin. Concurrent edits from two tabs are last write wins [ASSUMPTION]. Ordering changes use atomic database functions so they never half-apply.

### 16.6 Observability

- Every Edge Function request gets a request ID, returned in `X-Request-Id` and in error bodies, and logged with the outcome.
- A visitor or the owner can quote the request ID when reporting a problem.
- Logs are viewed in the platform dashboard. A front-end error reporting service is Future (ARCHITECTURE 17.2).

## 17. API Verification (acceptance tests)

These extend the gates in ARCHITECTURE 14.2 and DATABASE 15.2. They run in CI against the local Supabase stack, with the email provider replaced by a local stub through `MAIL_API_URL`.

### 17.1 submit-enquiry

1. A valid request returns 200 with `ok` and the same `submissionId`, and one row exists.
2. Re-sending the same `submissionId` returns the same 200 and still one row.
3. Each invalid case in the shared test vectors returns 400 with the correct field codes. All errors in one request are returned together.
4. An unknown field returns 400 `unknown_field`.
5. A filled honeypot returns an identical 200 and stores nothing.
6. Wrong method (405), wrong content type (415), an oversized body (413) including one sent without a truthful length (cap enforced while reading), and invalid JSON (400) behave as specified.
7. A disallowed Origin returns 403. An allowed origin gets exactly that origin echoed back and no wildcard. Preflight succeeds for allowed origins only.
8. The sixth valid request within an hour from one caller returns 429 with `Retry-After`. The daily ceiling returns 429 for everyone. Invalid requests do not consume the allowance.
9. If the rate-limit check or database is unavailable, the response is 503 and nothing is stored.
10. Responses and error bodies never contain submitted personal data, stack traces, keys or internal names. Logs contain no personal data. The caller's raw IP appears nowhere.
11. Every response carries `X-Request-Id`, `Cache-Control: no-store` and the standard headers.

### 17.2 Notifications

1. A created enquiry triggers one send attempt to the stub with the correct subject, Reply-To, plain-text body and idempotency key. Control characters and line breaks in input cannot alter email headers.
2. A stub failure leaves the enquiry stored and `notified_at` empty. The next retry run sends it exactly once and sets `notified_at`.
3. A configuration-style failure (401) stops a batch after the first call. A transient failure skips that item and continues.
4. `retry-notifications` returns 401 with no body for a missing or wrong secret, and 405 for the wrong method. It sends no CORS headers. Enquiries older than the retry window are not retried.

### 17.3 Data API, Auth and Storage

1. As an anonymous caller: PUB-1 to PUB-4 return only published data, no write succeeds anywhere, enquiries are unreachable, and private tables are not exposed.
2. A signed-in user who is not the admin gets no admin data, no storage writes and `false` from ADM-1.
3. As the admin: every operation in section 7 works, including the move functions, the status-only update on enquiries (other columns rejected), pagination with the correct `Content-Range`, and database rule errors mapping to the identifiers in 9.5.
4. Sign-up is rejected. A wrong password and an unknown email give the same generic result. Reset requests return the same neutral result in both cases.
5. Storage: allowed types and sizes upload. Wrong types, oversize files and overwrites are rejected. Non-admins cannot upload or delete. Listing the bucket returns nothing for anonymous callers.
6. No response from any surface ever contains the secret key, the Resend key, the IP salt or the cron secret. The secret key does not appear in any site file.

## 20. Assumptions Summary

1. One admin, low traffic (low hundreds of visits per week), fewer than about 100 published items, and enquiries in the tens to low hundreds per year.
2. The rate limits (5 per hour per caller, 100 per day), the 16 KB body cap, the 10-minute retry interval, batch size 20 and the 7-day retry window are starting points that can be tuned by configuration, without code changes to the contract.
3. Supabase and Resend behaviors stated here come from knowledge that may be out of date. Verify each at setup: the setting that allows a public function without a signed-in user, the trusted client-IP header, whether the email provider supports idempotency keys, Auth rate-limit ranges and password options, PostgREST single-object and count behavior, Storage cache-control and overwrite options, and the names of platform-injected variables.
4. Email delivery events (bounces, complaints) are not needed to meet the PRD. The retry job and the "Email not sent" indicator cover notification failure.
5. The shared enquiry contract (rules and test vectors) is the single source for field rules, used by the browser, the function and the tests.
6. A user with an older page open during a deploy is protected by the additive-first change policy (2.7).
7. The project is built in plain HTML, CSS and JavaScript: public pages call the APIs with `fetch`, admin pages use the vendored Supabase client, and the Edge Functions are written in JavaScript. No generated clients or SDKs are required on public pages.
